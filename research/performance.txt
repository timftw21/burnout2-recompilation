Root cause: extra-frame presentation happens in the same main-thread poll
used between guest execution slices and platform calls. Synchronous VSync
Present can block until the previous display entry completes. Once the queue
backs up, each poll can consume another display interval. Original game work
continues only in the small gaps, explaining low CPU usage and normal per-frame
game work despite very long source intervals. The old hidden-window timing
checks used VSync off and no work between source flips, missing this condition.

The window swap chain now exposes its frame-latency availability handle with
one queued frame. Interpolated display checks it with a zero timeout before
touching the back buffer and uses DXGI_PRESENT_DO_NOT_WAIT for submission.
A busy queue skips that display opportunity; it never blocks guest execution.
VSync stays selected and source pacing retains its 60 Hz interpolated cadence
and selected-rate interpolation-off behavior. If a nonblocking Present cannot
submit, the acquired frame slot remains available for the next attempt. Only
successful submissions advance the presented-frame counter. Window resizing
preserves the required swap-chain flag; the owned handle closes on destruction.

The existing hidden-window diagnostic now combines nine 1 ms CPU work slices
per source frame with a 1000 Hz / VSync-on extra-frame workload. This is a
bounded component check without game boot, not a gameplay FPS measurement.
