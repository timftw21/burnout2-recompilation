Building the game

Linux x86-64

Use a glibc-based distribution, Clang 19 or newer, LLD, Ninja, Git, CMake 4.2
or newer and a Vulkan 1.3 driver compatible with DXVK 2.7.1. On Ubuntu 24.04
the native dependencies are:

sudo apt install build-essential clang-19 lld-19 ninja-build git curl pkg-config patch libssl-dev libpng-dev libjpeg-dev libasound2-dev libpulse-dev libx11-dev libxext-dev libxrandr-dev libxcursor-dev libxi-dev libxfixes-dev libxss-dev libxtst-dev libwayland-dev libxkbcommon-dev libdrm-dev libgbm-dev libegl1-mesa-dev libgl-dev libdecor-0-dev libudev-dev libvulkan-dev spirv-headers flex bison libjson-perl

Install CMake 4.2+ separately if the distribution provides an older version.
Ensure clang, clang++ and ld.lld select the installed LLVM toolchain on PATH.
Run this from the extracted source directory:

bash Build.sh '/path/to/Burnout 2 - Point of Impact (USA).xiso.iso'

The builder fetches pinned SDL3 and DXVK Native, builds vkd3d-shader 2.1 with
the included shader bitcast fix, verifies the original executable, and compiles
the native game. Unchanged builds reuse the local compiler.
No Python or Wine is used. Only the standalone native shader compiler library
is built. FFmpeg is optional and needed only to import custom music.
Launch build/linux/Release/b2. The settings window uses native SDL file dialogs;
install an XDG desktop portal on Wayland if the desktop does not provide one.
Settings, saves, logs and imported music live beside the Linux executable.
Rebuilding refreshes game paths and preserves the other settings and saves.
Keep the source/build directories together; rebuild after moving them.

After dependency setup through Build.sh, developer builds use cmake --preset linux, then
cmake --build --preset linux-release (or linux-debug). Set B2_XBE and B2_EFFECTS
to verified extracted files to include the game. Without B2_XBE only b2-tool is
built. The native diagnostics have the same options as on Windows; use b2 and
b2-tool without the .exe suffix. CPU and effects reports are generated under
build/linux/generated/Release. No gameplay benchmark is implied by a native build.

Linux currently reports DLSS/FSR/XeSS D3D12 reconstruction, WARP, the D3D11
debug layer and hardware memory watches as unsupported. Native resolution,
higher internal resolutions and the shared D3D11 antialiasing paths use Vulkan.
For software offscreen rendering, select a software Vulkan ICD through its
standard loader environment; --warp remains Windows-only.

Linux validation (2026-10-21)

Ubuntu 24.04 under WSL2, Clang 19 and CMake 4.3.3 passed the native CPU, audio,
effects, input, storage and custom-music diagnostics. All 248 rendering cases
passed on llvmpipe. Hidden SDL3 window checks passed settings persistence,
resizing, widescreen and ultrawide presentation, with zero HLSL compilations.
Saves and music passed on ext4, including case-insensitive Xbox filename lookup.
Repeat setup preserved settings, saves and unchanged extracted-file timestamps;
an unchanged rebuild had no work to do. Crash reports retained guest context
from the owning thread. An authorized 29.978-second Airport Terminal 3 gameplay
benchmark also completed at 360 Hz selected, 1x, widescreen, interpolation and
V-sync off. Its 7.804 FPS used llvmpipe CPU rendering under WSL2; native Linux
GPU performance and audible playback remain unverified.

macOS Intel and Apple Silicon (bring-up)

Targets macOS 14+ and a Metal 3 GPU. Build with Xcode 16.3+ and its Metal/C++23
toolchain, CMake 4.2+, Ninja, Git and the libraries below.
Use the native shell on each architecture. Intel and Apple Silicon are separate
native builds; Rosetta and Wine are not used. Older Intel GPUs that cannot
provide DXMT's D3D11 feature level are unsupported.

With Xcode selected, install the native build dependencies using Homebrew:

brew install cmake ninja pkgconf openssl@3 libpng jpeg-turbo spirv-headers bison flex perl
if [ "$(uname -m)" = arm64 ]; then brew install mpfr; fi
export PATH="$(brew --prefix perl)/bin:$(brew --prefix bison)/bin:$(brew --prefix flex)/bin:$PATH"
cpan -T JSON
bash Build.sh '/path/to/Burnout 2 - Point of Impact (USA).xiso.iso'

Start build/macos/Release/b2. Keep the source/build folder: the native dynamic
libraries, extracted inputs, settings and saves remain there. Build.sh selects
Xcode's compiler and Homebrew's library paths, downloads the hash-verified official LLVM
15.0.7 library package required by DXMT, and builds the pinned dependencies
directly with CMake and make. It never calls Python or Meson. The native HLSL
compiler is used only during the build. The game runs D3D11 through native DXMT
and Metal, with an SDL-owned Metal view. FFmpeg is optional for music imports.

Intel retains native x87/SSE instruction helpers in Mach-O assembly. Apple
Silicon compiles each game instruction directly to native C++ functions, with
SoftFloat for the Xbox's 80-bit and IEEE arithmetic and MPFR for transcendental
functions. No guest instruction decoder, interpreter or JIT is used at runtime.
Unimplemented ARM instructions are reported during lowering. The existing
unresolved indirect game targets remain separate from host service bindings.
Intel hardware instruction-reference checks are explicitly unavailable on ARM;
the remaining diagnostics still exercise original game routines and services.
Unaligned atomic memory operations are explicitly unsupported on ARM.

No Mac was available during this bring-up. Native Mac linking, Metal rendering,
audible playback, full gameplay and performance require validation on both Mac
architectures. Windows-only D3D12 upscalers, WARP, D3D11 debug layers and hardware
memory watches remain unavailable. x87 transcendental results need comparison
on game scenes; MPFR does not reproduce the Pentium's internal approximations.

The manually triggered Native macOS build workflow compiles b2-tool on both
macos-15-intel and macos-15 (Apple Silicon), without uploading game files.
It has been prepared but not run. Build.sh --tools-only performs the same
source-only build locally and does not change game settings or saves. On ARM,
this also compiles the portable arithmetic core without needing a game image.

Windows x64

Install Visual Studio 2026 with Desktop development with C++, C++ CMake tools
for Windows and its Windows SDK, LLVM 22.1 or newer (Windows x64), CMake 4.2 or
newer, Git for Windows, and Ninja (ninja.exe).
Ninja is included with Visual Studio's C++ CMake tools for Windows component.
If it is missing, open Visual Studio Installer, choose Modify for Visual Studio
2026, and install that component under Individual components. Alternatively,
download ninja-win.zip from https://github.com/ninja-build/ninja/releases/latest,
extract it and add its folder to PATH. Reopen Build.cmd after installing it.
Download and extract the project source.
Double-click Build.cmd, select the supported US Xbox disc image, and wait for
the build. Click Open game folder and double-click b2.exe. No commands are needed.

The builder uses the native b2-tool to extract and verify the game executable
and read the effects image. It prepares data/local, configures and builds Release,
and updates game-file locations beside b2.exe after a successful build.
Other settings and saves are preserved. Use an Xbox XISO image;
full-disc dumps require conversion first. One build runs per source folder.
The installer shows each installation stage and a progress bar driven by
completed build tasks. Downloads, configuration and linking wait for the tool's
actual completion; the bar never advances on a timer. Open build log shows
details from build/setup/build.log. Closing the
window cancels the build and stops only workers started by the builder.

The first build downloads pinned dependencies and compiles the game ahead of
time. Later builds reuse unchanged outputs. Keep the source and build folders
to avoid starting over. Private game files, logs and output remain ignored.

an existing Visual Studio build, Build.cmd refreshes CMake's configuration while

Static CPU generation

B2_XBE enables ahead-of-time generation from entry, main, verified startup roots
and original constructor tables. Discovery follows direct calls, bounded switches
and installed static callbacks with a 16 KiB decoder cache. Limits: 65536 functions,
4096 instructions per function, 2097152 instructions total, 256 MiB source, 512
stable compilation shards. Unchanged shards keep their timestamps. There is no
runtime decoder, JIT or interpreter fallback.

Coverage reports:
build/windows/generated/Release/native_cpu.cpp.json
build/windows/generated/Debug/native_cpu.cpp.json

The report distinguishes compiled and proven closed functions, unresolved calls,
instruction failures, required services and native platform bindings. Partial
builds emit translatable functions with explicit boundaries for missing targets;
they do not establish complete coverage or boot. Native platform bindings preserve
visible behavior and calling conventions, and are reported separately.
The current batch translates over 35500 discovered functions without unsupported
instructions. Mutable indirect calls still need verified targets; this is not a
claim that every gameplay path or hardware service is covered.

Use b2-tool --help for bounded data reads, decoding, analysis and batch generation.
Seeds accept one address or entry per line, and table START END for verified
file-backed function-pointer tables. # starts a comment. A custom batch:
& .\build\windows\Release\b2-tool.exe batch data/local/default.xbe build/windows/generated/cpu-seeds.txt 65536 4096 build/native.cpp --allow-partial --report build/native.json

Incomplete batches exit 3. Without --allow-partial they publish only the report.
--replace permits replacing generated outputs. Wrong executables exit 2.

branches and control operations; diagnostics and invalid memory retain the

inputs. --bench-cpu reports both versions' timings and matching checksums.

Reports also include reserved/committed memory blocks
and the last failed allocation request
(size, alignment, requested address, lowest and highest address).

preferences retain their selected value.

fits its anamorphic framebuffer to 16:9 at presentation. HUD widgets retain their

gauges and their animated parts, and accounts for existing native split-screen

automatically and applies when starting or restarting a session. It defaults off.
Resolution scales colour/depth/feedback targets and raster/scissor rectangles;

a new game session or app restart. Diagnostic readback storage is allocated only

The added image feeds FXAA and upscaling. Shaders compile during
the build, and AO resources are allocated only while enabled. Settings apply

the added effect subtle. Screen-space AO cannot account for hidden geometry.
FXAA runs once on each completed internal-resolution image,
without changing original colour, depth or feedback targets. The settings and

prepare the extra visibility lists during loading; Original does neither. Each scene
camera retains its original range across camera switches, so scaling never
compounds. Traffic spawning, physics and the original three detail levels remain.
No extra reads or allocations occur during normal rendering. Changes apply on
start/restart. Existing enabled override settings migrate to 2x; an explicit
draw_distance=1, 2 or 4 takes precedence. Only the new setting is saved.
Intro skip finishes the original logo sequence at the PRESS START title screen
after required loading, preserving its normal controls and attract timeout.

Resolution selects the output size while upscaling is enabled. The game renders

Settings, including scancodes and game-file paths, save automatically in

Performance recording

Press F9 during play to start, reproduce the slowdown, then press F9 again to
save. Graphics / Performance diagnostics has the same controls. Recording stops
and saves after 60 seconds or at game exit. F8 also saves the current recording
alongside the frame/audio capture. performance-* folders contain performance.bin,
performance.json and a short performance.txt, under the usual build/captures path.

Recording measures exclusive main-thread wall time for guest code, kernel and
platform services, GPU command processing, drawing, buffer/texture uploads,
resource preparation, GPU waits, publication, display, Present,
UI, pacing and scheduler idle. It records source-frame intervals and counters
for draw/vertex volume, uploads, cache misses, copies, packets, fences and
presented/generated frames. Intentional pacing, scheduler idle and recorder
overhead are separated from work; frame/audio capture stalls are marked and
excluded from frame-percentile summaries. Service callbacks retain their parent
service category. CPU wall time includes host scheduling delays.

Guest checkpoints are sampled cooperatively at most once per millisecond;
original addresses and guest thread IDs guide bounded code analysis. They are
not per-function CPU timings. Twice per second, Windows resource samples record
process/main-thread CPU time, working set, private memory, page faults, handles,
I/O totals, resource counts and the process's local/shared GPU memory usage and
budget. Validity flags preserve unavailable measurements. Audio mix batches have
separate atomic elapsed-time and budget-overrun counters.

GPU timestamps sum nonoverlapping render, copy/resource and display
spans, excluding idle gaps and the ImGui overlay. An opt-in pool of eight frames
with 64 spans each avoids waits/flushes for timing; missing spans, invalid clocks
and results still pending at save are explicit. Normal play allocates no recorder
or extra timing pool and performs no sampling or per-frame disk writes.
Recorder capacity is 4096 source frames, 65536 checkpoint samples, 128 resource
samples and 2048 operation buckets; bound hits are reported.

Offline inspection and focused recorder validation require no game boot:

& .\build\windows\Release\b2-tool.exe inspect-performance CAPTURE/performance.bin build/checks/performance-report
& .\build\windows\Release\b2-tool.exe check-performance build/checks/performance

Use fresh output directories. Inspection rejects unsupported layouts, truncation
and oversized input before allocating bounded storage. Hidden window checks also
exercise source/display recording and nonblocking GPU result association.
Recorded CPU/GPU model, executable link stamp and display settings identify each run.
Component checks and instrumentation do not establish gameplay performance.

Dynamic vertex/index uploads append to unused buffer space and discard only
when wrapping, preserving in-flight draws. Identical shader constants reuse
their previous upload. Complete shader-upload packets copy in bounded blocks;
partial uploads retain their original lane/load-index behavior. Semaphore writes
at the same guest GPU command position share an event query, with separate
completion points for subsequent draws, clears, launches and flips. Offline
checks cover buffer wrapping, current attributes, shader-bank uploads and a
4096-write semaphore burst. Requested SDK fences wait only for their semaphore
value, using the original unsigned counter comparison across wraparound; an
already completed fence returns immediately. Query-pool capacity waits retire
only enough work to free a slot. Recording separates completion polling,
capacity waits, requested fences and full CPU-requested GPU-idle waits. Every
wait reason appears in the report, even below the hot-operation list's cutoff.
NV097 WAIT_FOR_IDLE submits queued draws in GPU order without stopping the CPU;
CPU-visible semaphores and explicit idle requests retain completion queries.
An offline 1024-barrier workload checks ordered output and one requested
semaphore, without creating completion queries for the GPU barriers.
Push-buffer RAM is validated once per bounded submission, with packet boundaries
still checked.
The original audio calculator retains derived listener orientation between
sources; moving listeners and immediate/deferred settings remain effective.
research/performance.txt records measured optimization batches. The latest
15-second Airport Terminal 3 benchmark measured about 223 original FPS on a
Ryzen 5 5600X and RTX 5060 Ti at 1x, widescreen, 240 Hz selected, interpolation
off and V-sync off, using the local LLVM profile-guided build. The sustained
240 FPS goal remains unmet; these measurements do not establish performance
on every track or an unprofiled installation build.

Interpolated presentation checks DXGI frame availability without waiting and

Optional LLVM profile-guided build

Normal builds leave B2_PROFILE_GENERATE off and B2_PROFILE_USE empty. To train
native compilation on a game scene, configure/build Release with:
cmake --preset windows -DB2_PROFILE_GENERATE=ON -DB2_PROFILE_USE=
cmake --build --preset release

Set LLVM_PROFILE_FILE to an absolute private filename containing %p before
launching the game. Use the normal timed controller/performance script; F9 (or
its performance control) resets compiler counters when recording starts, so
startup/menu navigation is excluded. Exit normally within 30 seconds of that
start. Compiler data is written on exit. This training executable is not an
FPS acceptance result. Clear the environment variable after training.

Merge the selected game profile, then build the optimized native executable:
llvm-profdata merge -o PATH/airport.profdata PATH/airport-PID.profraw
cmake --preset windows -DB2_PROFILE_GENERATE=OFF -DB2_PROFILE_USE=PATH/airport.profdata
cmake --build --preset release

Use absolute paths. Keep profiles private/generated, and rerun the actual
Airport benchmark and CPU/render diagnostics before accepting the result.
The optimized executable has no profiling counters. To restore ordinary
compilation, configure with both -DB2_PROFILE_GENERATE=OFF -DB2_PROFILE_USE=.

B2_AVX2 is an optional Release compiler target, disabled by default. Enable
with -DB2_AVX2=ON only for an AVX2-capable CPU and operating system; that binary
requires AVX2. Rebuild and check CPU, audio, rendering and actual game timings.
Use -DB2_AVX2=OFF to restore the portable x64 target.

Low-overhead game-frame benchmarking

Timed control scripts also accept benchmark 1 and benchmark 0. These record one
existing SDL timestamp at each original game flip, with an 8192-frame reserved
buffer and an automatic 30-second limit. They do not enable detailed per-call
CPU/GPU tracing. Use the same scene and controller events when comparing builds.
F9 and performance 1/0 retain the detailed diagnostic and are exclusive with a
frame-only benchmark. Reports go to build/captures/benchmark-*/benchmark.json,
including raw frame intervals, CPU/GPU/build identity, settings, dropped frames
and median/p95/p99/max frame times. Setup/loading precedes the measured segment.
