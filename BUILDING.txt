Building the game

Install Visual Studio 2026 with Desktop development with C++ and its Windows SDK,
CMake 4.2 or newer, and Git for Windows. Download and extract the project source.
Double-click Build.cmd, select the supported US Xbox disc image, and wait for
the build. Click Open game folder and double-click b2.exe. No commands are needed.

The builder uses the native b2-tool to extract and verify the game executable
and read the effects image. It prepares data/local, configures and builds Release,
and seeds game-file settings beside b2.exe only when settings do not already exist.
Existing settings and saves are preserved. Build progress appears in a small
window; Open build log shows details from build/setup/build.log. Closing the
window cancels the build and stops only workers started by the builder.

The first build downloads pinned dependencies and compiles the game ahead of
time. Later builds reuse unchanged outputs. Keep the source and build folders
to avoid starting over. Private game files, logs and output remain ignored.

Developer commands and native diagnostics

Windows x64, Visual Studio 2026 C++ tools, Windows SDK, CMake 4.2+ and Git are required.
Use C++23. Zydis is pinned and linked only into b2-tool, never the game executable.
Run PowerShell commands from the repository root. Private media and generated

Skip extraction for existing files: extraction refuses overwrites. Enabling
B2_XBE also requires the effects image; B2_EFFECTS can override its local path.
The target is verified against knowledge/supported_target.json.
Debug uses: cmake --build --preset debug

Static CPU generation

B2_XBE enables ahead-of-time generation from entry, main, verified startup roots
and original constructor tables. Discovery follows direct calls, bounded switches
and installed static callbacks with a 16 KiB decoder cache. Limits: 65536 functions,
4096 instructions per function, 2097152 instructions total, 256 MiB source, 512
stable compilation shards. Unchanged shards keep their timestamps. There is no
runtime decoder, JIT or interpreter fallback.

Coverage reports:
build/windows/generated/Release/native_cpu.cpp.json
build/windows/generated/Debug/native_cpu.cpp.json

The report distinguishes compiled and proven closed functions, unresolved calls,
instruction failures, required services and native platform bindings. Partial
builds emit translatable functions with explicit boundaries for missing targets;
they do not establish complete coverage or boot. Native platform bindings preserve
visible behavior and calling conventions, and are reported separately.
The current batch translates over 35500 discovered functions without unsupported
instructions. Mutable indirect calls still need verified targets; this is not a
claim that every gameplay path or hardware service is covered.

Use b2-tool --help for bounded data reads, decoding, analysis and batch generation.
Seeds accept one address or entry per line, and table START END for verified
file-backed function-pointer tables. # starts a comment. A custom batch:
& .\build\windows\Release\b2-tool.exe batch data/local/default.xbe build/windows/generated/cpu-seeds.txt 65536 4096 build/native.cpp --allow-partial --report build/native.json

Incomplete batches exit 3. Without --allow-partial they publish only the report.
--replace permits replacing generated outputs. Wrong executables exit 2.

CPU checks use native instruction references, original helpers, memory overlap
and alignment, floating state, TLS and fixed dispatch. Direct native calls retain
guest floating state; host services suspend it. Helper benchmarks are not FPS.
Consecutive x87 calculations compile into native instruction blocks, preserving
the original precision, order and floating exception state. Blocks stop at
branches and control operations; diagnostics and invalid memory retain the
individual compiled instructions. The CPU matrix check compares results and
state against unfused original code across rounding modes and overlapping
inputs. --bench-cpu reports both versions' timings and matching checksums.
Image checks also replay the original Crash-mode UI queue for empty, full and
partial bars, checking the compiled callback, vertices, colours and return stack
without booting. The user confirmed that Crash mode loads after the missing
callback was compiled; complete mode coverage remains unverified.
CPU checks also verify the restored Xbox reciprocal-square-root approximation,
including the original vector-normalization routine. Its small lookup table is
compiled into the executable and does not depend on the host CPU's estimate.
The user confirmed that the How to Play lesson demonstration now plays.
Audio checks exercise the shared PCM/Xbox ADPCM decoder and mixer without a game
or sound device. Native SDL3 playback supports buffers, loops, gain, frequency and
output routing. All five original DSP programs compile ahead of time into native
C++ functions (1754 instructions), with real delay-buffer transfers and shared
SDL3 processing. Sixty-five offline effects checks and forty audio checks pass,
including all 32 mix bins, headroom and replacement of the native effects image.
Play and write positions follow the original codec-block lead and loop wrapping;
play-region changes reset the loop region and normalize zero lengths.
Public effect-data updates, reads and commits use the native DSP state. Deferred
updates wait for commit; they do not enter private MCPX hardware paths or overwrite
the game's sample memory. Seven additional effect cases cover those operations.
3D geometry, distance curves, cones and Doppler use the original compiled SDK
calculators, including environmental direct/room attenuation and low-pass
coefficients. Native room sends feed the original reverb program. Native stereo
placement consumes their angles and keeps total stereo power constant.
FXIN voices return processed samples through
their own volume, 3D placement and room sends; both DSP mix-buffer windows share

stream packets and scene audio parity remain

The loader handles preload flags, zeroed storage, section references and lazy
loads. Boot diagnostics execute original entry and thread routines through the
static table. Reports include the stopping address, registers, stack, recent
execution, thread states and service calls. Native fibers retain compiled call
stacks; function/loop checkpoints allow time slices even during busy waits.
Reports also include reserved/committed memory blocks
and the last failed allocation request
(size, alignment, requested address, lowest and highest address).
Headless boot accepts at most 200000000 diagnostic checkpoints and retains a
30-second wall-clock limit. Larger checkpoint budgets let original busy waits
receive real timed callbacks and asynchronous disc completion.
The executable reaches original main and completes original graphics setup against a real D3D11
device. Original command buffers reach native draws, framebuffer flips and GPU
fences. Live execution reaches the original Single Player menu after its no-save
acknowledgements, loads the first driving lesson and renders its car, road,
traffic and HUD. Scripted acceleration advances the original car. A complete
race remains unverified. Add --frame OUTPUT.png
to save the actual submitted image; diagnostic file operations are also reported.
Use --memory ADDRESS:BYTES to include a bounded RAM slice in the report. Each slice
contains at most 4096 bytes; at most four slices are accepted. Addresses and sizes
can use decimal or 0x-prefixed hexadecimal notation.
Use --break ADDRESS[:HIT] to stop at an original native function or loop checkpoint.
HIT defaults to 1. Breakpoints and memory snapshots remain diagnostic-only.

Offline D3D11 rendering

& .\build\windows\Release\b2-tool.exe check-render build/checks/render --debug
& .\build\windows\Release\b2-tool.exe check-render build/checks/render-warp --warp --debug

Use fresh output directories. Runs save PNGs and structured adapter, failure and
GPU timing reports. The renderer supports all ten NV097 primitives, indexed draws,
depth, stencil, culling, scissor, polygon offset, blending, alpha tests, four texture
stages, register combiners and fog. The build translates the original vertex
programs and compiles the renderer, fixed-transform and GUI shaders into the
executable. The game has no shader compiler dependency. Shader constants and
render state change normally during play; no HLSL is compiled during drawing.
Successful shader generation is stamped so unchanged source files do not cause
the build to repeat shader compilation on subsequent incremental builds.
Launch programs execute on the GPU in offline checks. The game rejects any
vertex program missing from its compiled bank. Texture uploads support mip chains, cubemaps,
3D volumes, Morton layouts, RGB565, ARGB/XRGB and native DXT1/3/5. Projected
2D/3D sampling, pass-through, clipping and dependent AR/GB sampling are supported.
Vertex uploads can retain original interleaved streams, packed colors/normals,
shorts, bytes, float2H and current attributes instead of expanding every vertex.
Offscreen targets, including RGB565/Z16, can be copied and sampled on the GPU.
Texture bindings reuse matching rendered surfaces instead of stale RAM images.
GPU-produced cubemaps reuse six copied faces and refresh after producer writes.
XRGB bindings supply opaque alpha before alpha kill, including rendered textures.
Full packed color clears preserve the same GPU image across linear/swizzled
layout changes without a depth allocation; nonuniform reinterpretation is
explicitly unsupported. Texture sampling respects separate minification/magnification,
detail bias, mip-level limits and anisotropy. Samplers share a bounded cache
independently of blend/depth/raster state.
Surface clips retain their framebuffer storage; growth preserves color, depth
and stencil on the GPU.
Prepare resources before submission. Readback is an explicit offline operation.
The native tool retains its shader compiler for standalone component diagnostics.
For shader-bank research, use b2-tool compile-shaders XBE OUTPUT.cpp --replace.

The component suite passed 183 cases on RTX 5060 Ti and WARP with no D3D11
warnings, including relocated vertex programs, unused instruction slots and

Original GPU packet submission is supported. GPU fences and timing queries avoid
allocating queries or
waiting for timing samples during normal rendering.

SDL3 input supports Xbox gamepads and custom keyboard controls. Offline checks
cover remapping, cleared bindings, stick directions and unchanged gamepad input.
The executable opens an SDL3 window with persistent Dear ImGui settings in General,
Audio, Graphics and Controls tabs. Esc toggles settings; F1 remains an alias.
General selects the presentation limit, defaulting to 60 Hz independently of the
monitor, and has interpolation and frame-rate counter toggles. Selecting a rate
above 60 Hz enables interpolation; selecting 60 Hz or lower disables it. Manual
opt-outs survive save/load until another rate is selected. Original frames have
a separate 60 Hz limit. Absolute SDL3 deadlines avoid catch-up bursts after stalls
or rate changes; guest video stays at 60 Hz.
The scheduler presents additional images while servicing events/input between
original frames. V-sync can still limit presentation to the physical display.
Audio controls master volume and mute through SDL3's output gain. Graphics has
V-sync, fullscreen and internal resolution (1x-4x).
Resolution scales colour/depth/feedback targets and raster/scissor rectangles;
guest coordinates, texture addresses and gameplay are unchanged. Vertex mapping
keeps the host half-pixel origin independent of scale. Targets are created at
the selected scale when starting a game; changes during play require
a new game session or app restart. Diagnostic readback storage is allocated only
on request. The render-target budget accounts for scale and stays bounded.
The FPS overlay measures display and original-game frames separately over half
a second and is drawn at window resolution, after interpolation.
Controls allows a key per action, clearing bindings and restoring defaults.
Esc cancels an active key change; Esc/F1/F8/F9 remain reserved for the interface.
Settings, including scancodes, are saved in data/local/settings.cfg.

Interpolation is a D3D11 image pass, inactive at the default 60 Hz. It stores two
completed frames, estimates motion in both directions with four fixed-size
luminance levels, then warps them to the requested time. Weak/inconsistent motion and new
occlusions retain current pixels; scene changes and long gaps reset continuity.
ImGui is drawn afterwards. The additional display delay is about one source
frame. This improves presentation smoothness without raising gameplay speed;
occlusions/fast movement can still produce artifacts. All shaders compile during
the build, and disabling the feature avoids history copies and motion passes.
Hidden window diagnostics check saved/invalid bindings and settings, automatic
interpolation selection and saved opt-outs, the counter, all four tabs, Esc,
scaled targets, 60/120 Hz pacing, 60 Hz source frames at 120/144 Hz
presentation, translated images, endpoints, stationary HUD, new occlusions,
scene cuts and history reset. They export images and component GPU timing without
booting. These measurements do not establish gameplay FPS or visual parity.
Live logs report source FPS separately from presented FPS and generated frames.

Performance recording

Press F9 during play to start, reproduce the slowdown, then press F9 again to
save. Graphics / Performance diagnostics has the same controls. Recording stops
and saves after 60 seconds or at game exit. F8 also saves the current recording
alongside the frame/audio capture. performance-* folders contain performance.bin,
performance.json and a short performance.txt, under the usual build/captures path.

Recording measures exclusive main-thread wall time for guest code, kernel and
platform services, GPU command processing, drawing, buffer/texture uploads,
resource preparation, GPU waits, publication, display/interpolation, Present,
UI, pacing and scheduler idle. It records source-frame intervals and counters
for draw/vertex volume, uploads, cache misses, copies, packets, fences and
presented/generated frames. Intentional pacing, scheduler idle and recorder
overhead are separated from work; frame/audio capture stalls are marked and
excluded from frame-percentile summaries. Service callbacks retain their parent
service category. CPU wall time includes host scheduling delays.

Guest checkpoints are sampled cooperatively at most once per millisecond;
original addresses and guest thread IDs guide bounded code analysis. They are
not per-function CPU timings. Twice per second, Windows resource samples record
process/main-thread CPU time, working set, private memory, page faults, handles,
I/O totals, resource counts and the process's local/shared GPU memory usage and
budget. Validity flags preserve unavailable measurements. Audio mix batches have
separate atomic elapsed-time and budget-overrun counters.

GPU timestamps sum nonoverlapping render, copy/resource and display/interpolation
spans, excluding idle gaps and the ImGui overlay. An opt-in pool of eight frames
with 64 spans each avoids waits/flushes for timing; missing spans, invalid clocks
and results still pending at save are explicit. Normal play allocates no recorder
or extra timing pool and performs no sampling or per-frame disk writes.
Recorder capacity is 4096 source frames, 65536 checkpoint samples, 128 resource
samples and 2048 operation buckets; bound hits are reported.

Use fresh output directories. Inspection rejects unsupported layouts, truncation
and oversized input before allocating bounded storage. Hidden window checks also

Recorded CPU/GPU model, executable link stamp and display settings identify each run.
Component checks and instrumentation do not establish gameplay performance.

Dynamic vertex/index uploads append to unused buffer space and discard only
when wrapping, preserving in-flight draws. Identical shader constants reuse
their previous upload. Complete shader-upload packets copy in bounded blocks;
partial uploads retain their original lane/load-index behavior. Semaphore writes
at the same guest GPU command position share an event query, with separate
completion points for subsequent draws, clears, launches and flips. Offline
checks cover buffer wrapping, current attributes, shader-bank uploads and a
4096-write semaphore burst. Requested SDK fences wait only for their semaphore
value, using the original unsigned counter comparison across wraparound; an
already completed fence returns immediately. Query-pool capacity waits retire
only enough work to free a slot. Recording separates completion polling,
capacity waits, requested fences and full CPU-requested GPU-idle waits. Every
wait reason appears in the report, even below the hot-operation list's cutoff.
NV097 WAIT_FOR_IDLE submits queued draws in GPU order without stopping the CPU;
CPU-visible semaphores and explicit idle requests retain completion queries.
An offline 1024-barrier workload checks ordered output and one requested
semaphore, without creating completion queries for the GPU barriers.
Push-buffer RAM is validated once per bounded submission, with packet boundaries
still checked.
The original audio calculator retains derived listener orientation between
sources; moving listeners and immediate/deferred settings remain effective.
research/performance.txt records measured optimization batches; repeat gameplay
captures are still needed to establish sustained 60 FPS.
